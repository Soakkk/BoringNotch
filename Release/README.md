# Personal release

This GPL fork keeps upstream authorship and third-party licenses. Personal version, identifiers and feed live in `personal.json`; the Xcode project and application plist must agree. Keep the application name and installation path stable and increase the numeric build for each update. The app and XPC helper are universal arm64/x86_64, with minimum macOS 15 (the bundled MediaRemoteAdapter requires macOS15).

`Scripts/build-personal.sh` resolves only the committed package versions and compiles both targets without Apple certificates or provisioning. `Personal build` only runs manually, at an explicit full commit SHA. Its default unsigned ZIP preserves executable permissions and framework symlinks. Source archives, logs and private keys are never release assets.

Use `Scripts/personal-release.py --app PATH --sign-update PATH --output EMPTY_DIRECTORY --source-sha FULL_SHA`. Supply the existing matching Sparkle 2.9 exported private seed through `BORINGNOTCH_SPARKLE_PRIVATE_KEY` (a base64 32-byte seed). CI reads this only from the repository secret of that name, and only when signing is explicitly requested. The wrapper validates and matches the key without printing it, then passes it to the official Sparkle `sign_update` tool over standard input. Keep a protected offline backup; this personal distribution has no Developer ID fallback for a lost update key.

## Stable personal code identity

From 3.1.3, release apps use the same app-specific RSA-3072 code-signing certificate on every build. The public certificate is `codesign-certificate.pem`; `personal.json` pins its SHA-256 fingerprint. The private PKCS#12 and password are repository secrets `BORINGNOTCH_CODESIGN_P12_BASE64` and `BORINGNOTCH_CODESIGN_PASSWORD`, with a protected recovery copy outside the repository. Never regenerate this identity in a build or replace it to work around an import failure. Certificate renewal or loss requires a deliberate identity migration.

The signer checks both the committed certificate and the private identity against the pin, imports the identity into an isolated temporary keychain, restricts key use to the signing tool and removes the keychain afterward. No trusted-root installation or global trust changes are required. The PKCS#12 recovery export uses the macOS-provided `/usr/bin/openssl` and `-descert` for native Keychain import compatibility, with a high-entropy random password. Avoid OpenSSL 3 default PKCS#12 exports, which macOS may reject as a password error. Private files, their passwords and raw command errors never become release assets or log output.

The main app and helper keep their identifiers and certificate-based designated requirements across versions. Native regression tests sign different binaries, verify requirements in both directions and reject ad-hoc and unrelated-certificate replacements. Missing credentials stop packaging; publication refuses ad-hoc, unknown or mismatched certificate signing. Sparkle's separate Ed25519 key remains unchanged.

The initial migration from an ad-hoc release may require renewing existing privacy grants once. Subsequent versions must retain those grants; acceptance includes a real consecutive-version update on the destination Mac. Neither the app nor its updater resets or edits privacy permissions automatically.

The packager copies GPL and third-party licenses, signs nested executable code before enclosing bundles, preserves Sparkle service entitlements, expands the app's own Sparkle Mach lookup names, and keeps the app sandbox and hardened runtime. It creates a ZIP for Sparkle, a DMG containing an Applications shortcut, a release manifest, SHA256 checksums and an Ed25519-signed appcast. Both archives and the feed use the dedicated personal key. `SURequireSignedFeed` and `SUVerifyUpdateBeforeExtraction` enforce feed and archive authentication. Only these five files are permitted as release assets; the appcast is uploaded to `updater/personal-appcast.xml` after the release assets are public.

## Existing personal signing limitation

The personal certificate is self-signed and the app is not notarized by Apple. Gatekeeper trust and macOS privacy grants are separate from Sparkle's Ed25519 update authentication. The existing accessibility helper is deliberately outside the sandbox, as upstream; this workflow does not add privileges or change macOS security settings.

This personal identity has no Apple Team ID. Hardened runtime library validation normally permits only Apple libraries or code signed by the same team, and the application dynamically loads Sparkle and MediaRemoteAdapter. The previously confirmed loader failure therefore still requires the already-authorized app-only exception. `--allow-personal-library-validation-exception` adds only `com.apple.security.cs.disable-library-validation` to the main app's signing entitlements while retaining sandbox and hardened runtime; the old flag spelling remains an alias. It is off by default and recorded in the manifest. The workflow's existing `adhoc_library_exception` input retains its name for compatibility. No JIT, unsigned executable memory, DYLD environment, debug entitlement, global Gatekeeper, TCC or SIP changes are applied. A future Developer ID signed release should omit this exception.

References: [Apple code identity and privacy grants](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements), [Apple personal certificate signing](https://developer.apple.com/library/archive/technotes/tn2206/), [Sparkle setup and library validation](https://sparkle-project.org/documentation/), [Sparkle sandbox signing](https://sparkle-project.org/documentation/sandboxing/), [signed appcasts](https://sparkle-project.org/documentation/publishing/), [Apple library validation](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.disable-library-validation).

## Verification and publication

Unsigned preview runs never publish. Signing and publication are separate opt-ins. Publication must use a reviewed commit contained in `main`, a previously unused `personal-vVERSION` tag, and a build greater than the currently published appcast. The workflow publishes installer and update ZIP before committing the signed feed to `main`, so a client never sees a feed pointing at unavailable assets. A feed push failure is recoverable by committing the already-signed feed unchanged after verifying the assets.

Verify anonymous downloads with `shasum -a 256 -c SHA256SUMS`, then `swift Scripts/verify-update.swift TRUSTED_PUBLIC_KEY personal-appcast.xml` and `swift Scripts/verify-update.swift TRUSTED_PUBLIC_KEY UPDATE.zip ENCLOSURE_SIGNATURE`. Use the public key from the reviewed application, not from an untrusted download. `codesign --verify --deep --strict APP` verifies the extracted app. Launch and functional permission testing happen on the destination Mac before publication or installation acceptance.
