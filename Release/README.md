# Personal release

This GPL fork keeps upstream authorship and third-party licenses. Personal version, identifiers and feed live in `personal.json`; the Xcode project and application plist must agree. Keep the application name and installation path stable and increase the numeric build for each update. The app and XPC helper are universal arm64/x86_64, with minimum macOS 14.

`Scripts/build-personal.sh` resolves only the committed package versions and compiles both targets without Apple certificates or provisioning. `Personal build` only runs manually, at an explicit full commit SHA. Its default unsigned ZIP preserves executable permissions and framework symlinks. Source archives, logs and private keys are never release assets.

After replacing the public-key placeholder with a fresh Sparkle 2.9 public key, use `Scripts/personal-release.py --app PATH --sign-update PATH --output EMPTY_DIRECTORY --source-sha FULL_SHA`. Supply the matching Sparkle 2.9 exported private seed through `BORINGNOTCH_SPARKLE_PRIVATE_KEY` (a base64 32-byte seed). CI reads this only from the repository secret of that name, and only when signing is explicitly requested. The wrapper validates and matches the key without printing it, then passes it to the official Sparkle `sign_update` tool over standard input. Keep a protected offline backup; an ad-hoc app has no Developer ID fallback for a lost update key.

The packager copies GPL and third-party licenses, signs nested executable code before enclosing bundles, preserves Sparkle service entitlements, expands the app's own Sparkle Mach lookup names, and keeps the app sandbox and hardened runtime. It creates a ZIP for Sparkle, a DMG containing an Applications shortcut, a release manifest, SHA256 checksums and an Ed25519-signed appcast. Both archives and the feed use the dedicated personal key. `SURequireSignedFeed` and `SUVerifyUpdateBeforeExtraction` enforce feed and archive authentication. Only these five files are permitted as release assets; the appcast is uploaded to `updater/personal-appcast.xml` after the release assets are public.

## Personal signing limitation requiring review

There is no Apple signing certificate or notarization for this personal build. Gatekeeper trust and macOS privacy grants are separate from Sparkle's Ed25519 update authentication. The existing accessibility helper is deliberately outside the sandbox, as upstream; this workflow does not add privileges or change macOS security settings.

Ad-hoc signatures have no Apple Team ID. Hardened runtime library validation normally permits only Apple libraries or code signed by the same team, and the application dynamically loads Sparkle and MediaRemoteAdapter. Therefore an ad-hoc build may fail at launch with a dyld library-validation error even when every nested signature is valid. The packaging flag `--allow-adhoc-library-validation-exception` adds only `com.apple.security.cs.disable-library-validation` to the main app's signing entitlements while retaining sandbox and hardened runtime. It is off by default, recorded in the manifest, and must be reviewed against an actual launch failure before installation. No JIT, unsigned executable memory, DYLD environment, debug entitlement, global Gatekeeper, TCC or SIP changes are applied. A future Developer ID signed release should omit this exception.

References: [Sparkle setup and library validation](https://sparkle-project.org/documentation/), [Sparkle sandbox signing](https://sparkle-project.org/documentation/sandboxing/), [signed appcasts](https://sparkle-project.org/documentation/publishing/), [Apple library validation](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.disable-library-validation).

## Verification and publication

Unsigned preview runs never publish. Signing and publication are separate opt-ins. Publication must use a reviewed commit contained in `main`, a previously unused `personal-vVERSION` tag, and a build greater than the currently published appcast. The workflow publishes installer and update ZIP before committing the signed feed to `main`, so a client never sees a feed pointing at unavailable assets. A feed push failure is recoverable by committing the already-signed feed unchanged after verifying the assets.

Verify anonymous downloads with `shasum -a 256 -c SHA256SUMS`, then `swift Scripts/verify-update.swift TRUSTED_PUBLIC_KEY personal-appcast.xml` and `swift Scripts/verify-update.swift TRUSTED_PUBLIC_KEY UPDATE.zip ENCLOSURE_SIGNATURE`. Use the public key from the reviewed application, not from an untrusted download. `codesign --verify --deep --strict APP` verifies the extracted app. Launch and functional permission testing happen on the destination Mac before publication or installation acceptance.
